What BaseDbModel does, and what it leaves to you

A model is one table row with generated statements for it. Everything else is plain SQL.

BaseDbModel is not an ORM in the sense of relations, lazy collections, and query builders. It is a class that knows one table and its columns, and can generate the four single-row statements for them.

What you declare

A model subclass overrides __setupModel and, inside it, calls setTableName once and setColumn once per property. Each column records the property name, the column name, a BaseDbTypes value, and flags: whether it is part of the key, whether it is inserted, whether it is updated, whether it accepts null, and whether the database assigns it on insert.

What is generated

create inserts every SHOULD_INSERT column and copies lastInsertId() into the AUTO_INCREMENT property. read selects every column where every key column equals the property's current value. update sets every SHOULD_UPDATE column by key, and delete deletes by key. Values bind with the PDO type the column type maps to, and identifiers are quoted the way the connection's driver expects. generateClassQuery returns the same SQL as text so a repository can extend it with its own WHERE clause.

Each of the four returns a ReturnHelper. A PDOException becomes a message on it, not a thrown error.

Guards run first

Before a statement runs, the matching __can* method decides whether it may. __canCreate is where a model checks for duplicates or fills a timestamp; __canUpdate is where it refuses to update a row without an identifier. Return false for a plain refusal, or a bad ReturnHelper whose messages should reach the caller.

Values are coerced on the way in and out

When a row is read, DATETIME columns become DateTimeImmutable objects in UTC, BOOLEAN columns become booleans, and properties that already hold an EnumBase are rebuilt from the stored value or name. When a value is written, the reverse happens. Properties that are protected go through __set and __get, which also wrap STRING columns in a StringHelper; public typed properties skip the magic methods and hold plain values.

What is left to you

Lists, joins, searches, and pagination are prepared statements you write, typically in a repository class that returns models built with fromArray. Migrations are SQL files run by stoic-migrate. Transactions are beginTransaction and friends. The framework's own site template follows this split: *.cls.php files hold models, *.rpo.php files hold the queries that find them.

The tradeoff

You write more SQL than with a full ORM and you never wonder what SQL ran. The generated statements are logged with their parameters at info level, so a failing model explains itself in the log.
